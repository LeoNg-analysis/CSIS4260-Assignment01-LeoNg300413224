## 4. Part 1 – CSV vs Parquet Benchmarking

The dataset was converted into three Parquet formats: uncompressed, Snappy, and ZSTD.

### 4.1. Storage Size – Original Dataset

| Format               | File Size (MiB) |
| -------------------- | --------------: |
| CSV                  |           28.80 |
| Parquet Uncompressed |           12.54 |
| Parquet Snappy       |           10.03 |
| Parquet ZSTD         |            8.32 |

**Finding:** ZSTD achieved the smallest file size, reducing storage requirements by approximately 71% compared with CSV.

### 4.2. Read and Write Performance – 1x Dataset

| Format               | Average Read (s) | Average Write (s) |
| -------------------- | ---------------: | ----------------: |
| CSV                  |           0.0769 |            2.7313 |
| Parquet Uncompressed |           0.4943 |            0.2427 |
| Parquet Snappy       |           0.0296 |            0.1715 |
| Parquet ZSTD         |           0.0294 |            0.1813 |

Each test was repeated five times.

**Findings:**

- Parquet Snappy and ZSTD provided faster reading performance than CSV.
- All three Parquet formats achieved faster writing times than CSV.
- The uncompressed Parquet reading average was affected by a slow first run.

### 4.3. Scalability Results – 10x and 100x

| Scale | Format               | Read (s) | Write (s) | Size (MB) |
| ----- | -------------------- | -------: | --------: | --------: |
| 10x   | CSV                  |   1.4254 |   21.5874 |    288.01 |
| 10x   | Parquet Uncompressed |   0.2520 |    1.4966 |    125.41 |
| 10x   | Parquet Snappy       |   0.1856 |    1.6391 |    100.31 |
| 10x   | Parquet ZSTD         |   0.1794 |    1.7619 |     83.21 |
| 100x  | CSV                  |  24.9564 |  198.4294 |   2880.05 |
| 100x  | Parquet Uncompressed |   5.3140 |   43.5677 |   1254.12 |
| 100x  | Parquet Snappy       |   1.9489 |   45.2685 |   1003.11 |
| 100x  | Parquet ZSTD         |   1.8316 |   17.1818 |    832.07 |

The 10x and 100x datasets were generated by repeating the original data. Each scalability test was performed once, using chunked or batched reading to manage memory usage.

**Recommendation:** Parquet with ZSTD compression is recommended for this project because it provides excellent storage efficiency and strong reading performance. CSV remains useful for compatibility and data exchange.

## 6. Technical Indicators

Two technical indicators were calculated separately for each company.

### 6.1. Simple Moving Average (SMA)

- **SMA 20:** Average closing price over 20 trading days.
- **SMA 50:** Average closing price over 50 trading days.

SMA helps identify general price trends by smoothing short-term fluctuations.

### 6.2. Relative Strength Index (RSI)

- **RSI 14:** Momentum indicator calculated using 14-period average gains and losses.

RSI measures the strength of recent price movements on a scale from 0 to 100.

The dashboard includes reference levels at 30 and 70, commonly used to identify potentially oversold and overbought conditions.

**Data preparation:** Missing values at the beginning of each company's history were expected because rolling calculations require sufficient historical observations.

## 7. Machine Learning Methodology

### 7.1. Objective

The objective was to predict the next trading day's closing price for each stock using historical market data and technical indicators.

### 7.2. Features and Target

**Input Features:**

1. Current closing price
2. Trading volume
3. SMA 20
4. SMA 50
5. RSI 14
6. Daily return

**Target Variable:** Next trading day's closing price (`next_day_close`).

### 7.3. Machine Learning Models

Two machine learning algorithms were implemented:

- **Linear Regression:** A regression model that estimates the relationship between input features and the target price.
- **Random Forest Regressor:** An ensemble model combining multiple decision trees to capture nonlinear relationships.

A **Naive Baseline** was also evaluated. It uses the current closing price as the prediction for the next trading day.

### 7.4. Train/Test Split

A chronological 80/20 split was used instead of random splitting.

| Dataset  | Number of Records |
| -------- | ----------------: |
| Training |           471,894 |
| Testing  |           121,403 |

A gap was applied at the train/test boundary to avoid using a training target from the test period.

This approach reduces the risk of temporal data leakage and provides a more realistic historical backtesting evaluation.

## 8. Model Evaluation and Backtesting

The models were evaluated using three metrics:

- **MAE (Mean Absolute Error):** Average absolute difference between actual and predicted prices.
- **RMSE (Root Mean Squared Error):** Measures prediction error while giving greater weight to large errors.
- **R² (Coefficient of Determination):** Measures how well predictions explain variation in actual prices.

### 8.1. Overall Model Performance

| Model             |    MAE |    RMSE |     R² |
| ----------------- | -----: | ------: | -----: |
| Naive Baseline    | 0.9106 |  2.2485 | 0.9997 |
| Linear Regression | 1.8634 |  4.3491 | 0.9988 |
| Random Forest     | 1.3641 | 10.2399 | 0.9936 |

### 8.2. Key Findings

**1. The Naive Baseline performed best overall.**

The naive baseline achieved the lowest MAE and RMSE, outperforming both machine learning models on the overall test dataset.

**2. Random Forest had larger extreme errors.**

Although Random Forest achieved a lower MAE than Linear Regression, its RMSE was substantially higher. This indicates that some predictions contained large errors.

**3. Model performance varied across companies.**

Some high-priced stocks, particularly PCLN, produced large Random Forest errors. This suggests that the model struggled to extrapolate beyond price ranges represented in the training data.

**4. High R² does not guarantee superior forecasting performance.**

Both machine learning models achieved high R² scores, but neither outperformed the naive baseline.

**Conclusion:** These findings demonstrate why machine learning models should be compared against simple benchmarks rather than evaluated using R² alone.
